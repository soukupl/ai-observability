## Data conventions

- One deployment = one company (ADR-0028): there is no `company_id` anywhere. The `deployment` table holds exactly one
  row (unique index on `(true)`) with the name, slug, settings and project salt. `team_memberships` and per-user
  `budgets` point at `memberships(user_id)` (a team member must be a member; both go when the membership
  does). User columns of tokens, machines and telemetry point at the identity `users(id)`: removing a member keeps
  their history (ADR-0022 D1). Ingest writes only the token user's id (`lookup_ingest_token` requires a live
  membership; the ingest policies check `user_id = app_user()`).
- `users` is an identity: a **person** (e-mail unique case-insensitively, stored lower-case; logs in) or a **service
  user** (ADR-0029, brief Q9: no e-mail, never logs in, holds admin-made tokens; CHECK `users_email_kind`). Access,
  role (`admin` | `member`) and primary team live in `memberships` (at most one per user). There are no super admins.
- `teams.slug` (ADR-0030) is what a repository's `.ai-obs.json` names: unique, 1–63 of `a-z0-9-`. Omit it on insert
  and the trigger `teams_fill_slug` derives it from the name (`team_slug_base`, same rule as `slugifyTeamName()`;
  `-2`, `-3` … on a clash); once a turn references the team, `teams_slug_immutable` refuses a change (23514).
- `turns`, `runs` and `usage` carry denormalized `team_id` and `user_id`, so RLS can check each row
  on its own. `user_id` is null only on old `unverified` company-token turns (new rows are always `verified`); `turns.team_id` is null when neither the project mapping nor the user's primary team gives
  one (ADR-0035; `ingest_team_status` / `ingest_resolve_team`, the membership-checked dot-file lookup of ADR-0030, stay
  in the schema but ingest no longer calls them).
- Collector ids are stored in `external_id` columns, and `external_id` is unique, so ingest
  is idempotent. A run that arrives before its turn keeps `turn_id = null` and is linked later through
  `turn_external_id`. `parent_external_id` is linked to `parent_run_id` the same way.
- A turn row exists only once its `turn` event has arrived (it always has a session and its tokens). A
  `turn_outcome` / `turn_summary` that arrives first is parked in `pending_turn_patches` (one row per
  `turn_external_id`, null column = not patched) and moved onto the turn by
  `ingest_apply_pending_patch()` when the turn arrives (only onto an ownerless turn or one with the same
  owner: a parked patch remembers its sender in `user_id`, which cascades on user delete); unclaimed patches
  are dropped after 30 days (ingest, and the worker's retention pass)
  ([ADR-0015](../../docs/adr/0015-usage-rows-sum-by-turn.md)).
- `agent_sessions.title` / `title_source` are set only by `session_title` patches (ADR-0026). A title that arrives
  before its session is parked the same way in `pending_session_patches` (one row per
  `session_external_id`, sender in `user_id`) and moved onto the session by `ingest_apply_pending_session_patch()`
  when a session_start, turn_started, turn or session_end creates it; unclaimed titles are dropped after 30 days by the worker.
- Tokens: `input_tokens` does not include cache reads or writes. `reasoning_tokens` is the part of
  `output_tokens` spent on thinking, so it is never billed again. A turn's totals are the sum of all
  `usage` rows with that `turn_id`, and every aggregate sums by `turn_id` only. Ingest stores the turn
  event's usage (main agent plus sub-agents, as the collector reports it) as rows with `turn_id` set and
  `run_id = null`; each run's own usage rows have `run_id` set and `turn_id = null` (`app_ingest` cannot
  read token columns, so it cannot subtract one from the other). The seed also puts `turn_id` on run
  rows and keeps `run_id = null` rows as main-agent only. Both shapes sum correctly by `turn_id`; never
  sum all usage rows of a slice, and never add run rows on top of a turn's total
  ([ADR-0015](../../docs/adr/0015-usage-rows-sum-by-turn.md)).
- Cost is never stored. `estimate_cost_usd(model, day, input, output, cache_read, cache_write)` uses the
  `model_prices` row in effect on that day: the newest row with `effective_from <= day`. A day before the
  model's earliest row uses that earliest row (default prices start 2026-01-01, but history can be older),
  so cost is NULL ("n/a") only for a model with no price row at all. `priceInEffect(rows, day)` is the same
  rule in TypeScript. `migrate` adds any missing default prices and never overwrites edited rows.
- `daily_rollups` fold (worker `aggregateDay`, seed `insertRollups`; ADR-0015). One row per UTC day
  of the turn's `started_at` × team × user × project × harness × model × effort, where the columns split:
  - `turns`, `runs`, `duration_ms`, `phases_ms` and the outcome counts go to the row of the turn's **primary**
    `turns.model` × `turns.effort` (`'unknown'` when the turn has no model);
  - `input/output/cache_read/cache_write/reasoning_tokens` and `requests` go to the row of each **usage row's**
    `usage.model` × `usage.effort` (usage rows with that `turn_id`, sub-agents included).

  So a mixed-model turn adds token-only rows (`turns = 0`) for its sub-agent models, ≈ cost from rollups
  (model × day × tokens) equals ≈ cost from raw usage rows, turn counts per model are primary-model counts,
  and summing any column over all rows of a slice gives the raw total. Raw dashboard reads use the same
  split, so the two sources agree exactly.
- `daily_rollups` has no unique key. When a user is deleted, `user_id` is set to null, and that would
  break a unique key. The worker therefore recomputes a whole day slice in one
  transaction (delete + insert), and only for days whose raw data is still complete. Two rules protect
  permanent rollups ([ADR-0012](../../docs/adr/0012-retention-and-rollups.md)): rows of a deleted user are kept
  (the worker marks each row it writes in its id: UUID version digit 8, then `a` = had a user, `0` = none, so
  `user_id` null with an `8a` id is a deleted user's row), and a day whose raw turns were partly deleted is never
  rebuilt, only extended with turns created after the last rollup.
- `daily_skill_mcp_rollups` (ADR-0016) is written by the worker in the same slice transaction as `daily_rollups`, with the
  same mode (`rebuild` / `append`), the same picked turns and the same row-id marking (anonymised rows survive). One row
  per day × team × user × project × harness × the turn's primary model × kind × name × tool, counting the turn **and its
  runs**: a skill has one row (`tool = ''`); an MCP server has a total row (`tool = ''`) plus one row per tool. `turns` is
  the number of distinct turns in the group, so summing it over groups stays exact, but a server row is not the sum of its
  tool rows. Names are as ingested (plain or `sha256:`).
- **Outcome split (ADR-0017, migration 0007).** `daily_rollups` also keeps the tokens of turns whose outcome is failed
  / abandoned (`wasted_*`) or unknown (`unknown_*`), by the usage row's model × effort like the other token columns;
  `daily_skill_mcp_rollups` keeps the outcome counts of the turns in each row. Rows the worker (or seed) writes have
  `outcome_split = true`; rows from before 0007 on days whose raw turns are gone stay `false`, and the views exclude
  them from wasted spend and skill impact (and say so). MCP rows also carry `errors`, `denied`, `latency_ms` and the
  latency histogram `lat0`…`lat4` (migration 0009).
- **Runaway alerts (ADR-0018)** are rows of `runaway_alerts`, one per turn (unique per turn), written by
  the worker's `runaways` job and deleted with their turn or user. Thresholds come from `deployment.settings`
  (`runawayCostUsd`, `runawayHours`; CHECK-constrained, defaults `RUNAWAY_DEFAULTS`).
- **Run links (ADR-0020)** are rows of `run_links`, one typed edge (`item` | `sequence`) per turn key ×
  source × target × kind. The target run's event carries them, so ingest replaces a run's incoming links on every run
  event. `from_run_id` is resolved late like `parent_run_id` (the source may arrive after the target), `turn_id` like
  `runs.turn_id`; the external ids stay. Deleted with either run or the turn (FK cascades, which also cover
  retention: the worker has no grant on the table). A link is visible exactly when its target run is.
- Privacy: there are no columns for prompts, code, diffs or file paths. A CHECK constraint rejects
  project keys that look like local paths. Summaries are at most 140 characters.
- Timestamps are `timestamptz`. The aggregate functions group by UTC day.

## Roles and access

Each service connects with `dbFor('web' | 'ingest' | 'worker')`. That uses `DATABASE_URL_<SERVICE>`, or falls back
to `DATABASE_URL`. Every connection switches to its role through the `role` startup parameter, so RLS applies in dev
too. In production, set `DB_APP_<ROLE>_PASSWORD` and `migrate` turns that role into a LOGIN role. See ADR-0014.
`app_platform`, `DATABASE_URL_PLATFORM` and `DB_APP_PLATFORM_PASSWORD` are gone (ADR-0028).

| Role | Can |
|---|---|
| `app_web` | Dashboard reads and admin writes, always bound by RLS (below). It has full DML on `auth_*` / `magic_links`, which have no RLS because they are pre-login identity tables. It calls the public device-login functions without a context. |
| `app_ingest` | INSERT and UPDATE on sessions, turns, runs, usage, machines, projects, ingest_events, pending_turn_patches and pending_session_patches, only inside `withIngestContext(db, userId)`: rows with a `user_id` must belong to the token's user (`WITH CHECK user_id = app_user()`; an ownerless old row may be claimed, another user's row is invisible; without a context it sees no row at all). On `projects` it may insert only `key` / `display_name` and update only `last_seen_at`: the team mapping is the admins'. Its `run_links` access is limited to links whose target run it can see (its own or a claimable run). It can SELECT only identity columns (ids, external ids, team/user ids) plus, on `agent_sessions`, the liveness columns `current_turn_started_at`, `last_seen_at` and `ended_at` (0017, ADR-0027). It has no DELETE (except on `run_links`, whose rows a run event replaces), and it cannot read metrics, summaries, session titles, parked patch values, tokens or the deployment row (the token lookup returns what it needs). |
| `app_worker` | Reads telemetry, users, memberships, budgets and the deployment; writes daily_rollups; deletes expired raw rows, ingest_events, pending patches, expired auth sessions / magic links and old device codes; updates `budgets.notified_*` and `device_codes.status`; appends to audit_log. It cannot read tokens or auth secrets. |
| `app_definer` | NOLOGIN. It owns the `SECURITY DEFINER` functions and is never used to connect. |

### RLS context (app_web)

```ts
import { dbFor, withRlsContext } from '@ai-obs/db';
await withRlsContext(dbFor('web'), { userId, role: 'admin' | 'member' }, async (tx) => { … });
```

The context is set with `set_config(…, true)`, which is the same as `SET LOCAL` but takes bind parameters, so it ends
with the transaction. `withRlsContext()` rejects anything that is not a UUID or a valid role. The database checks the
context again:

- `app_user()` is `app.user_id` only while that user holds a membership; a removed member, an unknown id or no
  context sees nothing (not even the own `users` row).
- `app.role = 'admin'` only counts if the membership has `role = 'admin'` (`app_is_admin()`).
- A user is a lead only for teams where their `team_memberships.role` is `lead` (`app_led_teams()`).

Telemetry tables (`turns`, `runs`, `usage`, `agent_sessions`, `daily_rollups`, `daily_skill_mcp_rollups`,
`runaway_alerts`; `run_links` follow their target run; `machines` is admin-only in full mode):

| Mode (`deployment.settings.individualVisibility`) | Member | Lead | Admin |
|---|---|---|---|
| `aggregates-only` (default) | own rows | own rows; aggregates of led teams via `agg_*` | own rows; deployment-wide aggregates via `agg_*` |
| `full` | own rows | own rows + all rows of led teams | all rows |

The other tables:

- `deployment`: readable by app_web without a context (the header and the login page show the name); admins update
  `name`, `settings`, `updated_at`. The slug and the project salt are not editable.
- `teams`, `memberships`, `team_memberships` and `projects` are readable by every member. Only admins write them; on
  `teams` admins may change `name` and `slug` (the slug only until first use), on `memberships` only `role` and
  `primary_team_id`. Memberships are inserted and deleted only by the definer functions below.
- `users`: app_web reads only `id, email, name, kind, created_at` (column grant; `last_login_at` stays private) of
  current members (removed members' identities are hidden, D1). Admins may rename service users (`UPDATE (name)`,
  `kind = 'service'` only); people are never updated through app_web.
- Only admins can read or write `invitations`.
- `ingest_tokens` (ADR-0029): everyone creates only their own `manual` tokens (`created_by_user_id` = self); admins
  also create tokens for service users; `device` tokens come only from `device_exchange`. A user sees and revokes
  their own tokens, an admin every token (service users included). Leads have no token rights. A revoked token stays
  revoked, for every role (trigger `ingest_tokens_revoke_once`).
- `device_codes`: no app_web / app_ingest grants at all; only through the `device_*` functions.
- `budgets`: an admin manages all of them, a lead sees their teams' budgets, and a user sees their own.
- `audit_log`: anyone can append entries in their own name; only admins can read it.
- `model_prices`: readable by everyone, writable by admins (`ENABLE` RLS without `FORCE`, so the migrating owner's
  `ensureDefaultModelPrices()` keeps working). The web app writes the audit entry.

### Ingest pattern

```ts
const [tok] = await dbFor('ingest').execute(sql`select * from lookup_ingest_token(${hash})`);
await withIngestContext(dbFor('ingest'), tok.user_id, async (tx) => {
  // insert into ingest_events … on conflict (event_id) do nothing returning event_id   → de-dup
  // insert into turns (…, user_id = tok.user_id) … on conflict (external_id) do update set col = <bound value> returning id
});
```

In `ON CONFLICT DO UPDATE`, set columns to bound values, not `excluded.col`. Reading `excluded.col` needs SELECT on
that column, which `app_ingest` deliberately does not have (except the three liveness columns of `agent_sessions`,
0017, which ingest reads through the table name, e.g. `agent_sessions.ended_at`). A machine may be shared: the upsert
sets `user_id` to the sending user.

## Migrations

- `pnpm db:migrate` runs the Drizzle migrations from `migrations/` (`0001_roles_rls.sql` is one of them), adds missing
  default model prices, and sets role passwords from env. It is idempotent: Drizzle records each applied migration,
  and a migration never runs twice. All pending migrations run in one transaction.
- It needs the schema owner (`MIGRATE_DATABASE_URL`, else `DATABASE_URL`). That is a superuser in dev, or in
  production a role with `CREATEROLE` that can grant itself the `app_*` roles.
- **0018 refuses a database with more than one company.** Only the dev database ever had several: merge them first
  with `pnpm --filter @ai-obs/db db:merge-companies -- --survivor <slug> --name <name> --slug <slug> [--dry-run]`
  (rehearse on a `pg_dump` copy; `src/merge-companies.ts`). Restore the copy keeping owners (the `app_*` roles are
  cluster-wide, so no `--no-owner`), so the copy matches the live database; 0018 hands SECURITY DEFINER functions back
  to `app_definer` if a restore left them with another owner. The script sets the survivor's settings to the dev defaults
  (`full` / retention 395 / runaway 20 / `plain`) unless you pass `--visibility aggregates-only`, `--retention-days`,
  `--runaway-cost-usd` or `--project-naming`. Use `--url <postgres url>` to point at the copy; without it the script
  uses `MIGRATE_DATABASE_URL`, else `DATABASE_URL` (the live database from `.env`). Rollup rows are kept and re-pointed
  (sums asserted).
- Change the schema: edit `src/schema`, then run `pnpm db:generate`. **Every new table needs grants, `ENABLE` +
  `FORCE ROW LEVEL SECURITY`, a `definer_all` policy and per-role policies in a new hand-written migration**
  (`pnpm --filter @ai-obs/db exec drizzle-kit generate --custom --name …`; a custom migration copies the previous
  snapshot, so regenerate the snapshot from the schema afterwards, as 0018 did). Separate the statements in
  hand-written migrations with `--> statement-breakpoint`. `test/schema-drift.test.ts` fails when the snapshot or the
  migrated structure drifts from `src/schema`.
- If the owner is not a superuser, FORCE RLS applies to it as well. Data fixes then need `SET LOCAL ROLE app_definer`
  (the seed does this).
