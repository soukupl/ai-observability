[ADR-0008](../../docs/adr/0008-privacy-modes.md), [ADR-0014](../../docs/adr/0014-db-roles-and-connections.md),

## Data conventions

- Every tenant table has `company_id`. Composite foreign keys `(company_id, x_id)` stop a row from
  pointing at another company's team / session / turn / run. `team_memberships` and per-user `budgets` point at
  `company_memberships(company_id, user_id)` (a team member must be a company member; both go when the membership
  does). User columns of tokens, machines and telemetry point at the identity `users(id)`: removing a member keeps
  their history in that company (ADR-0022 D1). Ingest writes user ids only from `lookup_ingest_token` /
  `ingest_match_user_by_email`, which require a live membership.
- `users` is an identity (e-mail unique case-insensitively); company access, company role and primary team live in
  `company_memberships` (one per company × user). Super admins hold none (trigger-enforced both ways).
- `turns`, `runs` and `usage` carry denormalized `team_id` and `user_id`, so RLS can check each row
  on its own. `user_id` is null on `unverified` company-token turns; `turns.team_id` is null when neither a project
  mapping nor the user's primary team gives one.
- Collector ids are stored in `external_id` columns, and `(company_id, external_id)` is unique, so ingest
  is idempotent. A run that arrives before its turn keeps `turn_id = null` and is linked later through
  `turn_external_id`. `parent_external_id` is linked to `parent_run_id` the same way.
- A turn row exists only once its `turn` event has arrived (it always has a session and its tokens). A
  `turn_outcome` / `turn_summary` that arrives first is parked in `pending_turn_patches` (one row per
  `(company_id, turn_external_id)`, null column = not patched) and moved onto the turn by
  `ingest_apply_pending_patch()` when the turn arrives (only onto an ownerless turn or one with the same
  owner: a parked patch remembers its sender in `user_id`, which cascades on user delete); unclaimed patches
  are dropped after 30 days (ingest, and the worker's retention pass)
  ([ADR-0015](../../docs/adr/0015-usage-rows-sum-by-turn.md)).
- `agent_sessions.title` / `title_source` are set only by `session_title` patches (ADR-0026). A title that arrives
  before its session is parked the same way in `pending_session_patches` (one row per `(company_id,
  session_external_id)`, sender in `user_id`) and moved onto the session by `ingest_apply_pending_session_patch()`
  when a session_start, turn_started, turn or session_end creates it; unclaimed titles are dropped after 30 days by the worker.
- Tokens: `input_tokens` does not include cache reads or writes. `reasoning_tokens` is the part of
  `output_tokens` spent on thinking, so it is never billed again. A turn's totals are the sum of all
  `usage` rows with that `turn_id`, and every aggregate sums by `turn_id` only. Ingest stores the turn
  event's usage (main agent plus sub-agents, as the collector reports it) as rows with `turn_id` set and
  `run_id = null`; each run's own usage rows have `run_id` set and `turn_id = null` (`app_ingest` cannot
  read token columns, so it cannot subtract one from the other). The seed also puts `turn_id` on run
  rows and keeps `run_id = null` rows as main-agent only. Both shapes sum correctly by `turn_id`; never
  sum all usage rows of a company, and never add run rows on top of a turn's total
  ([ADR-0015](../../docs/adr/0015-usage-rows-sum-by-turn.md)).
- Cost is never stored. `estimate_cost_usd(model, day, input, output, cache_read, cache_write)` uses the
  `model_prices` row in effect on that day: the newest row with `effective_from <= day`. A day before the
  model's earliest row uses that earliest row (default prices start 2026-01-01, but history can be older),
  so cost is NULL ("n/a") only for a model with no price row at all. `priceInEffect(rows, day)` is the same
  rule in TypeScript. `migrate` adds any missing default prices and never overwrites edited rows.
- `daily_rollups` fold (worker `aggregateDay`, seed `insertRollups`; ADR-0015). One row per company × UTC day
  of the turn's `started_at` × team × user × project × harness × model × effort, where the columns split:
  - `turns`, `runs`, `duration_ms`, `phases_ms` and the outcome counts go to the row of the turn's **primary**
    `turns.model` × `turns.effort` (`'unknown'` when the turn has no model);
  - `input/output/cache_read/cache_write/reasoning_tokens` and `requests` go to the row of each **usage row's**
    `usage.model` × `usage.effort` (usage rows with that `turn_id`, sub-agents included).

  So a mixed-model turn adds token-only rows (`turns = 0`) for its sub-agent models, ≈ cost from rollups
  (model × day × tokens) equals ≈ cost from raw usage rows, turn counts per model are primary-model counts,
  and summing any column over all rows of a slice gives the raw total. Raw dashboard reads use the same
  split, so the two sources agree exactly.
- `daily_rollups` has no unique key. When a user is deleted, `user_id` is set to null, and that would
  break a unique key. The worker therefore recomputes a whole `(company_id, day)` slice in one
  transaction (delete + insert), and only for days whose raw data is still complete. Two rules protect
  permanent rollups ([ADR-0012](../../docs/adr/0012-retention-and-rollups.md)): rows of a deleted user are kept
  (the worker marks each row it writes in its id: UUID version digit 8, then `a` = had a user, `0` = none, so
  `user_id` null with an `8a` id is a deleted user's row), and a day whose raw turns were partly deleted is never
  rebuilt, only extended with turns created after the last rollup.
- `daily_skill_mcp_rollups` (ADR-0016) is written by the worker in the same slice transaction as `daily_rollups`, with the
  same mode (`rebuild` / `append`), the same picked turns and the same row-id marking (anonymised rows survive). One row
  per day × team × user × project × harness × the turn's primary model × kind × name × tool, counting the turn **and its
  runs**: a skill has one row (`tool = ''`); an MCP server has a total row (`tool = ''`) plus one row per tool. `turns` is
  the number of distinct turns in the group, so summing it over groups stays exact, but a server row is not the sum of its
  tool rows. Names are as ingested (plain or `sha256:`).
- **Outcome split (ADR-0017, migration 0007).** `daily_rollups` also keeps the tokens of turns whose outcome is failed
  / abandoned (`wasted_*`) or unknown (`unknown_*`), by the usage row's model × effort like the other token columns;
  `daily_skill_mcp_rollups` keeps the outcome counts of the turns in each row. Rows the worker (or seed) writes have
  `outcome_split = true`; rows from before 0007 on days whose raw turns are gone stay `false`, and the views exclude
  them from wasted spend and skill impact (and say so). MCP rows also carry `errors`, `denied`, `latency_ms` and the
  latency histogram `lat0`…`lat4` (migration 0009).
- **Runaway alerts (ADR-0018)** are rows of `runaway_alerts`, one per turn (unique per company × turn), written by
  the worker's `runaways` job and deleted with their turn or user. Thresholds come from `companies.settings`
  (`runawayCostUsd`, `runawayHours`; CHECK-constrained, defaults `RUNAWAY_DEFAULTS`).
- **Run links (ADR-0020)** are rows of `run_links`, one typed edge (`item` | `sequence`) per company × turn key ×
  source × target × kind. The target run's event carries them, so ingest replaces a run's incoming links on every run
  event. `from_run_id` is resolved late like `parent_run_id` (the source may arrive after the target), `turn_id` like
  `runs.turn_id`; the external ids stay. Deleted with either run or the turn (FK cascades, which also cover
  retention: the worker has no grant on the table). A link is visible exactly when its target run is.
- Privacy: there are no columns for prompts, code, diffs or file paths. A CHECK constraint rejects
  project keys that look like local paths. Summaries are at most 140 characters.
- Timestamps are `timestamptz`. The aggregate functions group by UTC day.

## Roles and access

Each service connects with `dbFor('web' | 'ingest' | 'worker' | 'platform')`. That uses
`DATABASE_URL_<SERVICE>`, or falls back to `DATABASE_URL`. Every connection switches to its role through
the `role` startup parameter, so RLS applies in dev too. In production, set `DB_APP_<ROLE>_PASSWORD`
and `migrate` turns that role into a LOGIN role. See ADR-0014.

| Role | Can |
|---|---|
| `app_web` | Dashboard reads and admin writes, always bound by RLS (below). It has full DML on `auth_*` / `magic_links`, which have no RLS because they are pre-login identity tables. |
| `app_ingest` | INSERT and UPDATE on sessions, turns, runs, usage, machines, projects, ingest_events, pending_turn_patches and pending_session_patches where `company_id = app.company_id`. It can SELECT only identity columns (ids, external ids, team/user ids) plus, on `agent_sessions`, the liveness columns `current_turn_started_at`, `last_seen_at` and `ended_at` (0017, ADR-0027). It has no DELETE (except on `run_links`, whose rows a run event replaces), and it cannot read metrics, summaries, session titles or parked patch values. |
| `app_worker` | Cross-company: reads telemetry, users, company memberships and budgets; writes daily_rollups; deletes expired raw rows, ingest_events, pending_turn_patches, pending_session_patches and expired auth sessions / magic links; updates `budgets.notified_*`; appends to audit_log. It cannot read tokens or auth secrets. |
| `app_platform` | Super admin: companies (all operations), users and company_memberships (admin contacts only: super admins and admin memberships), first-admin invitations, audit_log (only `platform.%` actions or rows without a company: it cannot read or forge tenant audit rows), model_prices, `platform_company_counts()`, `platform_invitee_status()`. It has **no grants** on telemetry, projects, teams or tokens. |
| `app_definer` | NOLOGIN. It owns the `SECURITY DEFINER` functions and is never used to connect. |

### RLS context (app_web)

```ts
import { dbFor, withRlsContext } from '@ai-obs/db';
await withRlsContext(dbFor('web'), { companyId, userId, role: 'admin' | 'member' }, async (tx) => { … });
```

The context is set with `set_config(…, true)`, which is the same as `SET LOCAL` but takes bind
parameters, so it ends with the transaction. `withRlsContext()` rejects anything that is not a UUID or a
valid role. The database checks the context again:

- If `app.user_id` is not a member of `app.company_id` (`company_memberships`), the caller sees nothing but
  their own `users` row.
- `app.role = 'admin'` only counts if that membership has `company_role = 'admin'`.
- A user is a lead only for teams where their `team_memberships.role` is `lead`.

Telemetry tables (`turns`, `runs`, `usage`, `agent_sessions`, `daily_rollups`; `run_links` follow their target run;
`machines` is admin-only):

| Mode (`companies.settings.individualVisibility`) | Member | Lead | Admin |
|---|---|---|---|
| `aggregates-only` (default) | own rows | own rows; aggregates of led teams via `agg_*` | own rows; company aggregates via `agg_*` |
| `full` | own rows | own rows + all rows of led teams | all company rows |

The other tables:

- `companies`, `teams`, `company_memberships`, `team_memberships` and `projects` are readable by everyone in the
  company. Only admins can write them, and admins can update only `name` and `settings` on `companies`;
  plan and status are changed by the platform. On `company_memberships` admins can update only `company_role` and
  `primary_team_id` (the composite FK keeps the team in the company); memberships are inserted and deleted only by
  the definer functions below.
- `users`: app_web reads only `id, email, name, is_super_admin, created_at` (column grant; `last_login_at` is a
  cross-company signal) of itself and of members of the active company. It cannot update or delete users.
- Only admins can read or write `invitations` and `identity_providers`.
- `ingest_tokens` (ADR-0022): `kind` is `company` (`aiobs_c_`, no user) or `user` (`aiobs_u_`). Everyone creates
  only their own user token; admins and leads (of any team) create company tokens. A member sees and revokes their
  own tokens, a lead also every company token, an admin every token of the company (user tokens included). A
  revoked token stays revoked, for every role (trigger `ingest_tokens_revoke_once`).
- `budgets`: an admin manages all of them, a lead sees their teams' budgets, and a user sees their own.
- `audit_log`: anyone can append entries in their own name; only admins can read it.

Revokes the member's user tokens and the company tokens they created there (returns them for the audit log), clears sessions working in that company, deletes the membership (cascade: team memberships, per-user budgets). Telemetry and rollups stay. |
| `company_has_user_capacity(company_id)` | definer only | Plan user limit check (memberships; free 3, team 50, business unlimited; mirrors `PLAN_LIMITS`). |
| `platform_company_counts()` | app_platform | Members and teams per company, for plan limits. |
| `platform_invitee_status(email, company_id)` | app_platform | `'super_admin'`, `'admin'` (of that company) or NULL. Never discloses a plain membership. |

Triggers (ADR-0022): `ingest_tokens_revoke_once` (42501 on any change of a set `revoked_at`),
`company_memberships_no_super_admin` / `users_super_admin_no_membership` (23514; race-free through a row lock),
`auth_sessions_mark_membership` (stamps `company_memberships.last_active_at` when a session starts in, or switches
to, a company; the login lands in the last active company).

### Ingest pattern

```ts
const [tok] = await dbFor('ingest').execute(sql`select * from lookup_ingest_token(${hash})`);
await withIngestContext(dbFor('ingest'), tok.company_id, async (tx) => {
  // insert … on conflict (company_id, event_id) do nothing returning event_id   → de-dup
  // insert … on conflict (company_id, external_id) do update set col = <bound value> returning id
});
```

In `ON CONFLICT DO UPDATE`, set columns to bound values, not `excluded.col`. Reading `excluded.col`
needs SELECT on that column, which `app_ingest` deliberately does not have (except the three liveness columns of `agent_sessions`, 0017, which ingest reads through the table name, e.g. `agent_sessions.ended_at`).

## Migrations

- `pnpm db:migrate` runs the Drizzle migrations from `migrations/` (`0001_roles_rls.sql` is one of them),
  adds missing default model prices, and sets role passwords from env. It is idempotent: Drizzle records
  each applied migration, and a migration never runs twice.
- It needs the schema owner (`MIGRATE_DATABASE_URL`, else `DATABASE_URL`). That is a superuser in dev,
  or in production a role with `CREATEROLE` that can grant itself the `app_*` roles.
- Change the schema: edit `src/schema`, then run `pnpm db:generate`. **Every new table needs grants,
  `ENABLE` + `FORCE ROW LEVEL SECURITY`, a `definer_all` policy and per-role policies in a new
  hand-written migration** (`pnpm --filter @ai-obs/db exec drizzle-kit generate --custom --name …`).
  Separate the statements in hand-written migrations with `--> statement-breakpoint`.
- If the owner is not a superuser, FORCE RLS applies to it as well. Data fixes then need
  `SET LOCAL ROLE app_definer` (the seed does this).

## Seed

`pnpm db:seed` deletes and rebuilds the demo companies **Acme** and **Globex** (and their `@acme.example` /
`@globex.example` users, which no longer cascade from a company). Acme contains:

- Teams Platform and Mobile.
- Users `alice` (company admin), `bob` (lead of Platform), `carol` and `dave`, all `@acme.example`.
- Projects `github.com/acme/billing` → Platform and `github.com/acme/mobile-app` → Mobile.
- 300 deterministic turns with sub-agent runs (Haiku / mini models, so many turns are mixed-model) and usage
  over the last 60 days, plus `daily_rollups` folded exactly like the worker does (see above).
- A $100 monthly cost budget for Platform.

Globex (Free plan, team Core, no telemetry) has `gina@globex.example` (admin, lead of Core), and alice is a member of
Core there too, so the company switcher has a choice and switching shows an empty dashboard.

It also creates a super admin from the first entry of `SUPER_ADMIN_EMAILS` (default `admin@example.com`), with no
memberships. Acme uses the default `aggregates-only` mode.

## Tests

`pnpm test` (or `pnpm vitest run --project db`):

- `test/rls.test.ts` runs against real Postgres. Start it with `docker compose up -d postgres`. The test
  uses `TEST_DATABASE_URL`, default `postgres://ai_obs:ai_obs@localhost:5432/ai_obs_test`. The database
  name must end in `_test`, because the test **drops and re-creates** it and then applies all migrations.
  It checks:
  - no cross-company reads, even with a forged context;
  - members see only their own rows;
  - leads see only their teams;
  - aggregates-only mode exposes no per-user rows to leads or admins except through `agg_*`, and full
    mode does expose them;
  - `app_platform` cannot read telemetry; nobody but ingest (identity columns), the worker and definer
    functions touches `pending_turn_patches` / `pending_session_patches`;
  - `app_ingest` cannot read turns, writes only into its token's company, and gets idempotent upserts;
  - `run_links` follow their target run (owner, lead in full mode, not another member), the link functions serve
    aggregates-only admins without user ids, and the worker's run deletes cascade into them;
  - tokens (ADR-0022): who may create company / user tokens, who sees which, the kind/user CHECK, lookup output;
  - one identity in two companies: each context sees only its company, `app_is_admin()` follows the membership,
    a non-member context sees only the own `users` row, `last_login_at` is unreadable for app_web, and
    `admin_remove_member` keeps telemetry, revokes tokens and clears sessions;
  - invariants: one-way revocation, no super-admin membership (also under concurrency), primary team in the same
    company, team membership needs a company membership, `last_active_at` stamping.

  Without Postgres the suite is skipped, and the reason appears in the suite name.
- `test/migration-0002.test.ts` (own database `ai_obs_m0002_test`) migrates to 0001, writes old-style
  placeholder turns, applies 0002 and checks the data fix: placeholders become parked patches, their runs are
  unlinked, rollup slices are re-queued or deleted, the watermark indexes exist.
- `test/migration-0003.test.ts` (own database `ai_obs_m0003_test`): the price fallback and the `agg_turn_list` order.
- `test/migration-0004.test.ts` (own database `ai_obs_m0004_test`): invitation consent and plan capacity, the user-token
  membership condition, team-bound git-e-mail matching, parked-patch ownership, platform audit scope and e-mail check, the
  project salt, as of 0004.
- `test/migration-0014.test.ts` (own databases `ai_obs_m0014_test`, `ai_obs_m0014b_test`): old-shape rows upgraded by
  0014 (membership backfill incl. `last_active_at`, dropped columns, revoked and retyped tokens, session company, kept
  turn, function owners, working RLS context) and the refusal for a super admin with a company.
- 0003, 0004 and 0014 pin their starting schema with `test/migrate-to.ts` (`migrateTo(url, tag)`: migrate up to that
  journal tag, then insert the default prices).
- `test/seed-rollups.test.ts` (own database `ai_obs_seed_test`) runs the demo seed and checks its rollups follow
  the fold above (tokens per usage model, turns per primary model), that its skill / MCP rollups equal the raw
  turns and runs, the demo memberships (alice in Acme and Globex, the super admin in none), and that a second run is
  idempotent.
